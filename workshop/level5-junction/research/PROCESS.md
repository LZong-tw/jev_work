# Level 5 Four Crossings：研究過程紀錄

時間為台灣時間（UTC+8）。分數一律指 tick 270（約 21:00）的分數，除非另外註明。

## 結論

- 每個 tick 決定燈號是算數問題，程式算得又準又穩；Jev 沒有程式拿不到的資訊，參與燈號只會加入雜訊。
- 最好的結果來自純程式規則加上三個設定：排隊權重 0.1、行人最久等 12 tick、下游壅塞扣分 0.15。本機模擬器 90 組情境平均比舊版多 +109.3 ± 19.0 分。
- 最大的方法論教訓：這個模擬器一點小差異就會放大，**單輪瀏覽器分數幾乎不能用來比較程式好壞**。前面多數版本的比較其實在比雜訊。

## 時間線

### 1. 原始程式的問題（10/03）

原版 `my_jev.py` 讓 Jev 直接選燈，送進去的資訊也有 bug：
- `describe()` 算好的燈號說明沒用到，Jev 只看到 `state: A.`。
- prompt 說「從歷史學習」，卻沒傳入 history。
- 夾雜錯字、街道名、公園描述等雜訊。

### 2. 程式算分、Jev 輔助（10/05 上午）

- 新增 `served()`、`demand()`：直接算每個燈號這個 tick 能過幾個、總共有幾個在排。
- 決策改成「程式算分 + `JEV_WEIGHT` × Jev 機率」，並加上行人等太久就強制放 W。
- `JEV_WEIGHT` 2.0 太大，會蓋過程式的計算，燈號每個 tick 亂跳，於是降到 0.5。

### 3. 找出自己寫的兩個 bug（看 log 找到）

- **W 跟車燈用同一把尺比**：行人燈和車燈輪流搶綠燈，車只拿到一半，傍晚越積越多，分數一路往下不回來。
  - 修法：`WALK_BATCH = 3`，行人人數打三折，讓人累積起來一次放。傍晚等待數降約三成。
- **左轉永遠輸**：左轉每 tick 最多過 2 台，直行加腳踏車可以過 4 個，所以左轉幾乎都排不到，傍晚排到 11–17 台。
  - 修法：`QUEUE_WEIGHT` 從 0.1 提高到 0.3。效果跟隨機誤差差不多。

### 4. 自動化測試與模式比較（v1，每種模式 3 輪）

改用 Playwright 開瀏覽器跑，一次並行多個 server。

| 模式 | 平均 |
|---|---|
| rule（只用程式） | 318.1 |
| hybrid（Jev 打破平手） | −2.7 |
| jev_guard（Jev 決定，程式防行人餓死） | −8428.3 |
| jev（Jev 完全自己決定） | −9458.9 |

讓 Jev 自己決定時，它太常選 W、左轉幾乎不放，城市整個塞爆。

### 5. 改 prompt 讓 Jev 選得更好（v2、v3）

- **v2**：把計分規則寫進 prompt，選項標上「加幾分、還剩幾個、幾個 tick 沒綠燈」，W 改由程式決定。
  - jev 從 −9459 進步到 −255，hybrid 卻從 −3 變成 −252。
- **v3**：加入尖峰時段預告。
  - hybrid 變成 −423、jev 變成 −356，沒有改善。
- 同一個設定，不同輪之間的分數就能差 800–1000 分。

### 6. 查 hybrid 為什麼兩極化

- Jev 每版都大約改掉 5% 的決定，而分數跟改掉的次數無關。
- 好壞取決於一大早的走向：幾個小差異 → W 變多 → 車的綠燈變少 → 越塞越多，之後一整天回不來。

### 7. v4：改行人規則，並補 Jev 缺的資訊

- 行人規則改成：3 人以上、6 tick 沒放才強制放 W；少於 3 人就等到 12 tick。
- 告訴 Jev 程式何時會強制放 W，以及最近 5 個 tick 的增減趨勢。

| 模式 | 三輪分數 | 平均 |
|---|---|---|
| rule | 517.4 / 477.8 / 468.8 | 約 488 |
| hybrid | −811.4 / −77.8 / 498.8 | 約 −130 |
| jev | −380.2 / −649.4 / −542.6 | 約 −524 |

rule 的三個分數不同，只是量分時落在不同 tick（271–278）。

### 8. v5：縮小 Jev 的影響（只在分數差 0.5 以內時讓 Jev 選）

hybrid 三輪 −570.2 / −838.6 / −634.4，平均約 −681，更差。

### 9. 轉向：從第一性原理研究（10/05 下午 – 10/06）

使用者提問：「會不會一開始的方向就不對了」，並要求不要以先前的嘗試為出發點，而是從第一性原理研究。研究流程：

1. **建模**：把 `city.html` 移植成 Python `sim.py`，逐 tick 對上 JS 原版。研究過程中跑出的程式和數據都在 `fp/`。
2. **分析**，三個方向同時進行：
   - 容量與分數上限
   - 控制法搜尋與參數掃描
   - 資訊價值：先知道未來能多幾分
3. **對抗式驗證**：重跑模擬，挑戰模擬是否準確、最佳分數是否碰巧、上限算得對不對。
4. **整合**：寫出 `STRATEGY.md`。

過程中遇到的狀況：
- 電腦當機，`/tmp` 被清掉，研究從頭重跑。
- 一個驗證 agent 排了太大的實驗，卡住超過 10 分鐘。隔天加上「每個指令 3 分鐘、最多約 20 次模擬」的限制後，從斷點接著跑完。

主要發現：
- 模擬器「確定但混沌」：同一個程式只要開場暖身多跑一步，分數就從 358.8 變成 468.8。
- 通過量已經接近上限，失分約 85% 來自車在等紅燈。
- 讓 Jev 在平手時二選一，就算事先知道未來，加的分也跟雜訊分不開。

各 agent 的報告原文在 `agent-reports/`。

### 10. 實作與驗證（10/06）

- `my_jev.py` 套用最佳設定，預設 `rule` 模式；`hybrid` 改成有限制的平手判斷：
  - 信心不到 0.6 不採用。
  - 塞車時段不問。
  - 不推翻強制的行人燈。
  - Jev 出錯時照程式原本的選擇。

## 學到的事

1. **先問「這個決定，程式算得出來嗎？」** 算得出來就交給程式。Jev 適合需要理解語意、規則寫不出來、錯了也不會被放大的判斷。
2. **在混沌系統裡，單輪結果不能比較。** 要先有一個能大量重跑的模擬器，用成對比較、看平均和標準誤。
3. **研究要從問題本身出發**，不要從自己先前的嘗試出發。前五版都在「Jev 該怎麼放」裡打轉；改成先問「最好解長什麼樣」，一次就找到 +109 分。
4. **看 log 找 bug 有效。** W 搶綠燈和左轉餓死這兩個問題，都是從每個 tick 的排隊數字找出來的。
